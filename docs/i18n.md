# Internationalisation (i18n)

> Translation standards, plugin choice, URL strategy, and REST API language filtering.

---

## Plugin: Polylang (free)

Install via Composer (WPackagist):

```bash
composer require wpackagist-plugin/polylang
```

- Danish is the default language (no URL prefix)
- English is the secondary language (`/en/` prefix)
- Polylang handles slug translation per language — CPT slugs are always registered in English in code (e.g. `event`), and Polylang maps the Danish URL slug (`begivenhed`) at the language layer
- No hard-coded Danish strings in PHP or JS — everything goes through translation functions

---

## URL Structure

| Language | Event archive | Single event |
|---|---|---|
| Danish (default) | `/begivenheder/` | `/begivenhed/my-event/` |
| English | `/en/events/` | `/en/event/my-event/` |

Slug translations are configured in Polylang settings, not in PHP.

## PHP — Translation Functions

Always use WP translation functions. Text domains: `vandrekalender-events` (plugin), `vandrekalender-theme` (theme).

```php
// Basic string
__( 'Walking events in Denmark', 'vandrekalender-events' )

// Escaped for HTML output (use this in templates)
esc_html__( 'Walking events in Denmark', 'vandrekalender-events' )

// With echo
esc_html_e( 'Walking events in Denmark', 'vandrekalender-events' )

// With variable substitution
sprintf(
    /* translators: %s: event title */
    esc_html__( 'Sign up for %s', 'vandrekalender-events' ),
    esc_html( $event_title )
)
```

Never output a bare English string — always wrap in a translation function.

---

## JavaScript — Translation Functions

Use `@wordpress/i18n` (already a dependency via `@wordpress/scripts`).

```js
import { __, sprintf } from '@wordpress/i18n';

// Basic string
__( 'Filter events', 'vandrekalender-events' )

// With variable
sprintf( __( 'Showing %d events', 'vandrekalender-events' ), count )
```

Register the script translations in PHP so WP loads the `.json` translation file:

```php
wp_set_script_translations( 'your-script-handle', 'vandrekalender-events' );
```

## REST API — Language Filtering

Polylang adds a `lang` parameter to all REST API requests.

```
GET /wp-json/vandrekalender/v1/events?lang=da
GET /wp-json/vandrekalender/v1/events?lang=en
```

The custom REST API endpoints in `class-event-rest-api.php` must pass `lang` through to `WP_Query` so Polylang's query filter applies. Without this, the endpoint returns events from all languages.

```php
// In get_events() — add lang param support
if ( $request->get_param( 'lang' ) ) {
    $args['lang'] = sanitize_text_field( $request->get_param( 'lang' ) );
}
```

Default behaviour when no `lang` param is passed: return the default language (Danish).

## Generating Translation Files

The plugin's Danish translation lives in `wp-content/plugins/vandrekalender-events/languages/`:

| File | What it is | Committed |
|---|---|---|
| `vandrekalender-events.pot` | Template: every translatable string in PHP, JS and `block.json` | Yes |
| `vandrekalender-events-da_DK.po` | Danish translations (edit this one) | Yes |
| `vandrekalender-events-da_DK.mo` | Compiled `.po`, read by PHP | **Yes**: the servers have no step that compiles it |
| `vandrekalender-events-da_DK-<md5>.json` | Danish for one JS script (editor panel, block editors), read by `wp_set_script_translations()` | Yes |

The `<md5>` in a JSON file name is the MD5 of the script's path relative to the plugin, e.g. `build/resources/event-meta-fields/index.js`. Only the **built** scripts (`build/…`) are loaded, so JSON files for source paths (`blocks/…/edit.js`, `resources/…`) are deleted.

Run all steps after adding or changing strings (from the repo root; `npm run build` in the plugin first, so the built JS is current):

```bash
L=wp-content/plugins/vandrekalender-events/languages

# 1. Template from PHP, block.json and JS. Do NOT exclude "resources": WP-CLI
#    matches the name anywhere, so it would also drop build/resources/ and with
#    it every string in the event editor panel.
./wp.sh i18n make-pot wp-content/plugins/vandrekalender-events $L/vandrekalender-events.pot \
  --exclude=node_modules,vendor

# 2. Merge into the Danish file, drop strings the code no longer uses.
msgmerge --update --backup=none --no-wrap $L/vandrekalender-events-da_DK.po $L/vandrekalender-events.pot
msgattrib --no-obsolete --no-wrap -o $L/vandrekalender-events-da_DK.po $L/vandrekalender-events-da_DK.po

# 3. Translate every empty msgstr and fix every "#, fuzzy" entry (msgmerge's
#    fuzzy guesses are often wrong), then check and compile.
msgattrib --untranslated $L/vandrekalender-events-da_DK.po   # should list only the names below
msgattrib --only-fuzzy $L/vandrekalender-events-da_DK.po     # should list nothing
msgfmt --check -o $L/vandrekalender-events-da_DK.mo $L/vandrekalender-events-da_DK.po

# 4. JS translations, then keep only the files for built scripts.
./wp.sh i18n make-json $L --no-purge
for f in $L/*.json; do grep -q '"source":"build' "$f" || rm "$f"; done
```

Left untranslated on purpose (names, not text): the plugin name "Vandrekalender Events", its URI, the author name and the brand "Vandrekalender".

Front-end view scripts (`blocks/*/view.js`) have no translatable strings. Their text comes from PHP (`render.php` or `wp_interactivity_state()`), so they need no JSON files.
